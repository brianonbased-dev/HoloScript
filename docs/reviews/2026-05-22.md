### R-01 · P1 · `sim_run_paid` returns stub billing data

**Commit:** 54e057e4  
**File:** `packages/mcp-server/src/simulation-billing-tools.ts:167–197`

The `sim_run_paid` tool's "run" path computes a real quote but returns hardcoded stub data for all execution and charge fields:

```typescript
charge: { backend: 'test-ledger', charged_credits: priceCredits, real_money: false },
execution: {
  billable_seconds: params.estimate_seconds * 0.8, // placeholder; real execution fills this
  ...
  wall_seconds: params.estimate_seconds * 0.8,
```

The comment says "placeholder; real execution fills this" — but there is no code path that fills it. The `invokeSimBillingHarness` function constructs subprocess args (line 104–118) but never actually calls a subprocess; it falls through to the local math path regardless of `dispatch_mode`. Every paid run via MCP returns `real_money: false` and a hardcoded 80% wall_seconds estimate.

**Impact:** Any consumer of `sim_run_paid` receipts (including Paper 35 evidence chain) is ingesting fabricated billing data. The reconcile field also computes a refund against the fake execution seconds, compounding the fiction.

**Recommended fix:** Gate on `dispatch_mode === 'fleet'` and either (a) actually invoke `scripts/sim_solver_executor.py` via `execFileAsync` or (b) throw `NOT_IMPLEMENTED` until the harness integration is wired. Do not return fake execution data under a real billing schema.

### R-02 · P1 · `deterministicHash` outputs only 64-bit entropy

**Commit:** efefeb2a  
**File:** `packages/core/src/compiler/SpatialPartitionPass.ts:468–487`

The function is documented as producing a "64-char hex" provenance hash to match SHA-256 output width. The actual implementation:

```typescript
const hex0 = h0.toString(16).padStart(8, '0'); // 32-bit word → 8 chars
const hex1 = h1.toString(16).padStart(8, '0'); // 32-bit word → 8 chars
const base = (hex0 + hex1).repeat(4).slice(0, 64); // 16 chars × 4 = 64 chars
```

The 64-char output is the 16-char (64-bit) hash **repeated verbatim four times**. It is not 256 bits of entropy — it is 64 bits with visual padding. Any consumer checking hash length for validation will pass; any consumer checking for uniqueness will have a collision probability of `1/2^64` per pair instead of `1/2^256`.

The accumulator seed `h1 = 0xd1e4a9f3` is also not a standard FNV offset basis, making the independence of `h0`/`h1` questionable.

**Recommended fix:** Use `createHash('sha256').update(input).digest('hex')` (Node.js `crypto` is already imported in the broader codebase). The custom hash should be removed entirely.

### R-03 · P1 · `merkleRoot` field is XOR-chain, not a Merkle root

**Commit:** efefeb2a  
**File:** `packages/core/src/compiler/SpatialPartitionPass.ts:491–507`, `SpatialPartitionResult.merkleRoot` field (line 179)

The public interface field is named `merkleRoot`. The implementation XOR-folds all sorted `provenanceHash` byte arrays:

```typescript
bytes[i] ^= parseInt(byteHex, 16) || 0;
```

XOR-fold has two structural weaknesses that a Merkle root does not:

1. **Cancellation**: two anchors with identical `provenanceHash` values cancel each other to zero bytes. A scene with an even number of duplicate anchors is indistinguishable (via root) from a scene with none of them.
2. **No inclusion proof**: a recipient cannot prove a single anchor is included without the full anchor set. Merkle trees support `O(log n)` membership proofs.

The commit message correctly labels this "XOR-chain" internally, but the public interface names it `merkleRoot`, creating a false contract with downstream consumers (e.g., anything checking `result.merkleRoot` for integrity).

**Recommended fix:** Rename the field to `anchorSetXorFold` or similar, and update the type documentation. If a true Merkle root is needed, implement pairwise SHA-256 hashing. This is a naming + correctness issue, not just cosmetic.

## P2 Findings

### R-04 · P2 · `nlPrompt` partial sanitization in generated browser JS

**Commit:** 55024480  
**File:** `packages/core/src/compiler/PhoneSleeveVRCompiler.ts:1295, 1462`

The `buildBrittneySovereignModule()` method emits JavaScript that runs in the browser. The `generate` function in the emitted code sanitizes user input with only:

```javascript
nlPrompt.replace(/"/g, '\\"');
```

The sanitized value is then embedded in a template literal:

```javascript
return `orb '...' { prompt: "${nlPrompt.replace(/"/g, '\\"')}" ... }`;
```

A user passing a backtick in `nlPrompt` would close the template literal. A user passing `${...}` would invoke template expression evaluation. Neither is escaped.

**Impact:** The generated `.holo` fragment could be syntactically broken or contain unintended expression evaluation in the browser context. If the output of `generate()` is ever passed to `eval()` or `innerHTML` by a downstream consumer, this is a full code injection.

**Recommended fix:** Escape backticks, `$`, and backslashes in addition to double quotes before embedding in a template literal. Alternatively, do not embed the prompt as a string literal in a template — store it in a `data-*` attribute or pass it through a validated serialization path.

### R-05 · P2 · `brittneyLocalPath` interpolated into single-quoted JS string

**Commit:** 55024480  
**File:** `packages/core/src/compiler/PhoneSleeveVRCompiler.ts:1295, 1462`

Both the new `buildBrittneySovereignModule()` and the existing inline block embed the option value directly:

```typescript
const localPath = '${this.opts.brittneyLocalPath}';
```

If `brittneyLocalPath` is sourced from external configuration and contains a single quote, the generated JavaScript breaks. If it contains `'; injectedCode(); //`, the generated script executes injected code in the browser.

The default is `/assets/brittney-15m.wasm` (safe), but the option is user-supplied (`PhoneSleeveVRCompilerOptions.brittneyLocalPath?: string`) with no sanitization at assignment (line 157).

**Recommended fix:** Sanitize with `JSON.stringify(this.opts.brittneyLocalPath)` before interpolating, or use an attribute/data channel rather than embedding in a JS string literal.

### R-06 · P2 · `set -uo pipefail` missing `-e` in onstart bootstrap

**Commit:** 21da7eb8  
**File:** `scripts/mesh-deploy/vast-onstart-bootstrap.sh:27`

The script opens with `set -uo pipefail`. The missing `-e` means command failures in the body do not terminate the script unless the failure is the last command in a pipeline, or explicitly guarded with `|| { exit N; }`.

The critical guards (`|| { exit 2; }`) are present for `git clone` and `cd`. However, several intermediate lines (`git fetch`, `git reset`, `chmod +x`) have no failure guard. A `git reset --hard origin/main` failure leaves the worker running an outdated checkout silently, which will produce hard-to-diagnose job failures on the fleet.

**Recommended fix:** Change to `set -euo pipefail`. The existing `|| echo WARN` and `|| echo FATAL; exit 2` patterns are compatible with `-e` as written.

### R-07 · P2 · API key fallback reads `.env` from disk without line guard

**Commit:** ea8feca4  
**File:** `scripts/hardware-bench.mjs:773–784`

The script falls back to reading `HOLOSCRIPT_API_KEY` from `.env` files on disk when the env var is not set:

```javascript
if (line) { apiKey = line.split('=')[1]?.trim(); break; }
```

`line.split('=')[1]` returns only the content before the second `=` — a value like `key=abc=def` would be truncated to `abc`. More importantly, the script then logs the POST result to stdout, making it easy to accidentally surface the key in CI/CD job logs if stdout is captured.

The key is used directly in an `x-mcp-api-key` header (line 822). No length or character validation is performed before use.

**Recommended fix:** Use `line.split('=').slice(1).join('=').trim()` to handle `=` in values. Add a `process.env.HOLOSCRIPT_API_KEY` check before touching disk. Consider suppressing the POST status line when running in CI (`process.env.CI`).

### R-08 · P2 · JSDoc says SHA-256 but hash is of filename string only

**Commit:** efefeb2a  
**File:** `packages/core/src/compiler/SpatialPartitionPass.ts:133–140`

The `SpatialAnchor.provenanceHash` JSDoc states:

> "Provenance hash (SHA-256 hex of sourceFile if available, otherwise a deterministic content-hash...)"

The implementation:

```typescript
? deterministicHash(`file:${src.sourceFile}:${src.maxSplats}`)
: deterministicHash(`${src.objectName}:${lodLevel}:${src.maxSplats}`);
```

Neither branch computes a SHA-256. Both use the weak custom hash (see R-02). The "if sourceFile is available" branch hashes the **filename string**, not the file contents. Two different files with the same name and splat count produce identical `provenanceHash` values.

**Impact:** Downstream integrity checks (e.g., Paper 35 audit receipt chain using `evidenceHash`) that rely on `provenanceHash` uniqueness are structurally weaker than documented.

**Recommended fix:** For the `sourceFile` branch, use `createHash('sha256').update(fs.readFileSync(sourceFile)).digest('hex')` (or a cached async variant). For content-only anchors, the custom hash is acceptable if renamed and documented accurately.
