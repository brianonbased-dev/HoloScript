### P2 — Animated property references undeclared trait

**File:** `examples/stress-tests/monsoon-atelier-stable-diffusion-2026-05-23.holo`  
**Object:** `CanvasRight`

`CanvasRight` uses `@animated` to drive `property: "material.emissive_intensity"` but declares only `@stable_diffusion` — no `@emissive` trait is present on this object. The two other canvases (`CanvasCenter` has `@glowing`, `CanvasLeft` has `@glowing`) do not share this pattern. If the runtime resolves `material.emissive_intensity` strictly from declared traits, this animation is a no-op at best and a runtime warning/error at worst.

The intent (the canvas brightens sympathetically during the lightning strobe) is clearly right. Fix: add `@emissive { intensity: 0.02, color: "#b0b8c8" }` to `CanvasRight`, making the base state consistent with the animation's `value: 0.02` floor.

```diff
  object "CanvasRight" @stable_diffusion @animated {
+   @emissive { intensity: 0.02, color: "#b0b8c8" }
    @animated {
      property: "material.emissive_intensity"
```

### P2 — Voice biometric ReID in example with no privacy annotation

**File:** `examples/stress-tests/liminal-archive-walkable-navmesh-speech-encounter-2026-05-23.holo`  
**Object:** `Theodora`

```
@speech_aware_encounter {
  reid_backend: "reid_local"
  reid_confidence_threshold: 0.72
  …
}
```

`reid_local` collects voice fingerprints (biometric identifiers under GDPR Art. 9 and CCPA § 1798.140). Stress-test files are regularly copied into production templates. Before this file is referenced in docs or distributed:

1. Add a comment block above `Theodora` explaining that `reid_local` retains voice embeddings and must be paired with explicit user consent + a data-retention policy before production use.
2. Consider whether `fallback_to_text: true` should be the only default shown in example code, with ReID opt-in documented separately.

This is a policy gap, not a code defect — hence P2 rather than P0 — but it is the kind of detail that causes compliance incidents when examples become templates.

### P3 — `@emissive` applied to a `type: "point_light"` object

**File:** `examples/stress-tests/monsoon-atelier-stable-diffusion-2026-05-23.holo`  
**Object:** `LightningFlash`

```
object "LightningFlash" @emissive @animated {
  type: "point_light"
  …
  @emissive { intensity: 0.0, color: "#c8d8ff" }
```

`@emissive` is a mesh surface trait; it has no defined semantics on a light source. The parser accepts it (no syntax error), but a light node has no `material.emissive` surface to emit from. The `@animated` on `intensity` (the light's own property) is the correct mechanism and already present. The `@emissive` block is dead configuration on this object and should be removed to avoid confusing future trait authors who look at this as a canonical usage example.

### P3 — `realtime` omitted on two of three `@stable_diffusion` canvases without explanation

**File:** `examples/stress-tests/monsoon-atelier-stable-diffusion-2026-05-23.holo`  
**Objects:** `CanvasLeft`, `CanvasRight`

`CanvasCenter` (LCM, 12 steps) sets `realtime: true, streaming: true`. `CanvasLeft` (SDXL, 22 steps) and `CanvasRight` (SDXL, 28 steps) omit both. This is likely intentional — SDXL at 22–28 steps cannot sustain real-time generation — but there is no comment explaining the distinction. Someone copying the SDXL canvas blocks as a template may not realise they are getting one-shot-on-load generation rather than continuous update. A one-line comment (`// SDXL at 28 steps: one-shot generation on scene load, not real-time`) would close the gap.
