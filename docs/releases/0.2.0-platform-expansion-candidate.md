# HoloScript Systems 0.2.0 platform-expansion candidate

## Decision

The 0.2 line makes `@holoscript/systems` platform-neutral and moves native binaries into exact
optional packages:

- `@holoscript/systems-win32-x64@0.2.0`
- `@holoscript/systems-linux-x64@0.2.0`

The meta package selects only the current host package. Missing, unsupported, or mismatched platform
packages fail with an explicit diagnostic. The native receipt advances to `hs-machine-v33`, including
deterministic multi-file module projects.

## Immutable boundary

`@holoscript/systems@0.1.0`, its `v0.1.0` GitHub release, tarball, Windows binary, WebAssembly
artifact, integrity, and receipts remain immutable. The 0.2 candidate reuses the exact 0.1 portable
WebAssembly artifact and records that provenance; it does not rebuild history or mutate `latest`.

The candidate publishes only to the `next` tag after all local receipts pass. Promoting `latest`
requires separate post-publication npm/GitHub readback and cold consumers on both supported hosts.

## Build and verification

The Windows x64 compiler builds on the owned host. The GNU/Linux x64 compiler builds in the pinned
`rust:1.91-bookworm` container. Both packages are packed twice and must produce identical tarball
digests. Fresh Windows and Linux npm consumers install the meta tarball plus their platform tarball,
compile the v33 module example, and run an executable that exits 5.

```powershell
node scripts/holo-ci/build-systems-0.2-candidate.mjs --source-commit <HEAD> --json
node scripts/holo-ci/check-systems-0.2-candidate.mjs --json
```

Canonical policy is
[`systems-0.2-candidate-manifest.json`](../../scripts/holo-ci/systems-0.2-candidate-manifest.json).
Generated artifacts and the build receipt live under `artifacts/releases/0.2.0-candidate/`.
